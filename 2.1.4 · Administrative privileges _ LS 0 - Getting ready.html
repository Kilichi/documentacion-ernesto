2.1.4 · Administrative privileges

🛡️ 2.1.4 · Administrative privileges

Recuperamos cómo realizar tareas administrativas de forma controlada

🎯 Objetivo
Recordar la diferencia entre un usuario normal y root, comprender cuándo necesitamos privilegios administrativos y utilizar sudo de forma controlada, comprobando siempre el resultado de nuestras acciones.

Hasta ahora hemos trabajado con usuarios, grupos, archivos, directorios, propietarios y permisos. Sin embargo, algunas operaciones sobre el sistema no pueden ser realizadas por cualquier usuario.

Instalar software, modificar determinados archivos de configuración, gestionar usuarios o cambiar algunos propietarios son tareas administrativas. Linux restringe estas operaciones para proteger el sistema frente a modificaciones accidentales o no autorizadas.

🔎 ¿Por qué necesitamos recordarlo?

Cuando comencemos a configurar nuestros servidores DNS-LDAP, Git, Web y FTP, tendremos que realizar operaciones que afectan al sistema. Para ello necesitaremos saber cuándo son necesarios privilegios administrativos y utilizarlos únicamente cuando corresponda.

👤 1 · A normal user

Un usuario normal puede trabajar con los recursos para los que dispone de los permisos necesarios, pero no puede modificar libremente cualquier elemento del sistema.

Podemos comprobar nuestra identidad mediante:

$ whoami
$ id
💡 Concepto

Trabajar habitualmente como usuario normal limita el impacto de errores y evita realizar modificaciones administrativas innecesarias.

👑 2 · The root user

root es la cuenta administrativa principal de Linux. Su identificador es UID 0 y dispone de amplias capacidades para administrar el sistema.

⚠️ Más privilegios también implican más responsabilidad

Un comando ejecutado con privilegios administrativos puede afectar a todo el sistema. Por eso debemos comprobar cuidadosamente qué comando vamos a ejecutar, sobre qué recurso y con qué opciones.

🛡️ 3 · Using sudo

En Ubuntu podemos utilizar sudo para ejecutar una operación concreta con privilegios administrativos cuando nuestro usuario está autorizado para hacerlo.

$ sudo COMMAND

Por ejemplo:

$ sudo chown root server.conf

En este caso, sudo no forma parte de chown. Estamos solicitando ejecutar ese comando concreto con privilegios administrativos.

🤔 4 · Do I need sudo?

No debemos añadir sudo automáticamente delante de cualquier comando. Primero debemos preguntarnos si la operación realmente necesita privilegios administrativos.

Operación ¿Privilegios administrativos?
Consultar tu directorio con ls Normalmente no.
Crear un archivo dentro de tu directorio personal Normalmente no.
Crear o modificar cuentas de usuario Sí.
Modificar determinados archivos del sistema Sí.
Instalar o eliminar software del sistema Sí.

👥 5 · Who can use sudo?

En nuestro entorno Ubuntu, la pertenencia al grupo sudo es uno de los mecanismos utilizados para conceder a un usuario la posibilidad de ejecutar comandos administrativos mediante sudo.

Podemos comprobar los grupos de un usuario mediante:

$ groups admin_temp
$ id admin_temp
🔗 ¿Recuerdas 2.1.1 · Users and groups?

Allí utilizamos:

$ sudo usermod -aG sudo admin_temp

Ahora podemos comprender mejor su finalidad: Estamos modificando la cuenta admin_temp para añadirla al grupo sudo sin eliminar sus grupos suplementarios anteriores.

🔍 6 · Check your privileges

También podemos consultar qué operaciones puede ejecutar nuestro usuario mediante sudo.

$ sudo -l

El objetivo no es memorizar la salida, sino comprobar si el usuario dispone de autorización para ejecutar tareas administrativas.

🧠 7 · Work with the necessary privileges

Antes de utilizar sudo:

  1. Identifica qué quieres conseguir.
  2. Comprueba sobre qué recurso actuará el comando.
  3. Determina si realmente necesitas privilegios administrativos.
  4. Ejecuta la operación.
  5. Comprueba el resultado.
⚠️ sudo no es la solución a cualquier error

Si un comando falla, añadir sudo sin analizar la causa puede ocultar un problema de permisos, una ruta incorrecta o una operación mal planteada. Primero interpreta el error.

🧩 Mini challenge · An administrative change
🔗 Continuamos con el reto anterior

En 2.1.3 · Ownership and permissions protegiste el archivo ~/daw_lab/config/server.conf. Vamos a continuar trabajando sobre ese mismo recurso.

Comprueba primero que dispones del archivo:

$ ls -l ~/daw_lab/config/server.conf

Ahora necesitamos que el archivo de configuración pase a ser propiedad de root, simulando una situación en la que un recurso deja de pertenecer a nuestro usuario y pasa a estar administrado por el sistema.

Tu tarea:

  1. Comprueba el propietario actual de server.conf.
  2. Intenta cambiar su propietario a root sin utilizar inicialmente sudo.
  3. Observa e interpreta el resultado obtenido.
  4. Determina por qué esta operación necesita privilegios administrativos.
  5. Realiza correctamente el cambio utilizando los privilegios necesarios.
  6. Comprueba nuevamente el propietario del archivo.
🔍 Antes de terminar

Debes poder explicar por qué la primera operación no puede realizarla tu usuario normal, por qué utilizamos sudo y cómo has comprobado que el cambio se realizó correctamente.

🩺 2.2.4 · Network diagnostics

Aprendemos a comprobar una comunicación y localizar dónde falla

🎯 Objetivo
Recuperar un procedimiento básico de diagnóstico de red que nos permita comprobar la configuración de una máquina, verificar su conectividad e identificar en qué punto puede encontrarse un problema de comunicación.
🔗 Continuamos desde 2.2.3

Ya sabemos configurar una dirección IPv4 estática mediante Netplan y comprobar el resultado utilizando ip addr e ip route.

Pero que una máquina tenga aparentemente una configuración correcta no demuestra que pueda comunicarse con el resto de equipos.

🤔 Una situación muy habitual

Has configurado el servidor Web, pero no consigue comunicarse con otra máquina de nuestra Red interna.

¿Por dónde empezarías a buscar el problema?

🧠 1 · Diagnose, don't guess

Cuando una comunicación falla, modificar configuraciones al azar puede generar nuevos problemas y dificultar todavía más el diagnóstico.

Trabajaremos siguiendo un orden: comenzaremos comprobando nuestra propia máquina y avanzaremos progresivamente hacia el destino.

🌐 Configuración
→
🔌 Interfaz
→
🗺️ Ruta
→
📡 Conectividad
💡 Importante:

El objetivo no es ejecutar muchos comandos, sino utilizar cada comprobación para decidir cuál debe ser el siguiente paso.

🔌 2 · Is the interface ready?

Antes de investigar direcciones o rutas, podemos comprobar que la interfaz de red existe y está activa.

$ ip link

También podemos consultar únicamente una interfaz:

$ ip link show enp0s3

Recuerda algunos elementos que ya vimos en 2.2.1 · Network interfaces:

Información ¿Qué nos indica?
enp0s3 La interfaz que estamos comprobando.
UP La interfaz está habilitada administrativamente.
LOWER_UP Existe enlace en la capa inferior.

🌐 3 · Is the IPv4 configuration correct?

Si la interfaz está disponible, comprobamos que posee la dirección IPv4 y el prefijo que debería tener según nuestro plan de direccionamiento.

$ ip addr show enp0s3

Para el servidor Web esperamos encontrar:

inet 192.168.X.154/24
⚠️ Si el valor no coincide

Antes de continuar buscando un problema de conectividad, revisa la configuración de Netplan. Si nuestra propia configuración es incorrecta, debemos corregirla primero.

🗺️ 4 · Does the system know where to send the traffic?

Una dirección correcta no es suficiente cuando queremos alcanzar destinos situados fuera de nuestra red. También debemos comprobar las rutas que conoce el sistema.

$ ip route

Para nuestro servidor Web esperamos encontrar información similar a:

default via 192.168.X.253 dev enp0s3
192.168.X.0/24 dev enp0s3 proto kernel scope link src 192.168.X.154

Debemos comprobar que existe la ruta hacia nuestra Red interna y que la ruta predeterminada utiliza 192.168.X.253.

📡 5 · Can we reach another machine?

Una vez comprobados la interfaz, la dirección y las rutas, podemos comenzar a realizar pruebas de conectividad.

Para ello utilizaremos ping, que nos permite enviar mensajes de prueba a otra dirección IP y observar si obtenemos respuesta.

$ ping DIRECCION_IP

Podemos limitar el número de pruebas para evitar dejar el comando ejecutándose continuamente:

$ ping -c 4 DIRECCION_IP

🪜 6 · Test step by step

No probaremos destinos al azar. Comenzaremos cerca de nuestra máquina y ampliaremos progresivamente el alcance de las pruebas.

1️⃣ Local system
$ ping -c 4 127.0.0.1

Comprobamos la comunicación con la interfaz de loopback de la propia máquina.

2️⃣ Own IPv4 address
$ ping -c 4 192.168.X.154

Comprobamos nuestra propia dirección IPv4.

3️⃣ Gateway
$ ping -c 4 192.168.X.253

Comprobamos si podemos alcanzar la interfaz interna de DNS-LDAP, que utilizarán nuestros equipos como puerta de enlace.

4️⃣ Another internal machine

Finalmente, comprobamos la comunicación con otro equipo de nuestra Red interna.

Por ejemplo, desde Web hacia Git:

$ ping -c 4 192.168.X.104

🧠 7 · Interpret the result

Ejecutar ping no es suficiente. Debemos observar el resultado y utilizarlo para decidir qué investigar a continuación.

Resultado ¿Qué podemos investigar?
La interfaz no tiene la IPv4 esperada Revisar nuestra configuración de Netplan.
No aparece la ruta esperada Revisar dirección, prefijo y rutas configuradas.
Responde nuestra máquina pero no otro equipo Revisar la configuración de ambos extremos y su conexión a la Red interna.
Responde un equipo interno Hemos obtenido evidencia de conectividad IP entre ambos equipos.
⚠️ Cuidado con las conclusiones

Que un ping no reciba respuesta no demuestra, por sí solo, que el equipo esté apagado o que toda la red haya fallado. El resultado es una pista dentro del proceso de diagnóstico.

☁️ ¿Probamos Internet?

Todavía no esperamos que nuestros servidores internos puedan alcanzar Internet a través de DNS-LDAP.

DNS-LDAP dispone de una interfaz en la Red interna y otra en la Red NAT, pero tener dos interfaces no convierte automáticamente una máquina en router.

Esa funcionalidad se configurará más adelante.

🧭 8 · Build your diagnostic procedure

Cuando aparezca un problema de comunicación, utiliza un procedimiento ordenado antes de modificar la configuración.

1. 🔌 Comprueba la interfaz con ip link.
2. 🌐 Comprueba la dirección y el prefijo con ip addr.
3. 🗺️ Comprueba las rutas con ip route.
4. 📡 Realiza pruebas de conectividad progresivas con ping.
5. 🧠 Utiliza cada resultado para decidir qué elemento debes investigar a continuación.

🧩 Mini challenge · Where is the problem?

Situación

Has configurado el servidor Web con la dirección correspondiente a tu rango, pero necesitas demostrar que su configuración de red es correcta y que puede comunicarse con otros equipos de la Red interna.

Realiza un diagnóstico ordenado y demuestra:

  1. ¿Qué interfaz de red estás utilizando?
  2. ¿Cuál es su estado?
  3. ¿Qué dirección IPv4 y prefijo tiene configurados?
  4. ¿Qué rutas conoce el sistema?
  5. ¿Qué puerta de enlace aparece configurada?
  6. ¿Puedes alcanzar la interfaz interna de DNS-LDAP?
  7. ¿Puedes alcanzar al menos otro servidor de la Red interna?
🔍 Antes de terminar

No presentes únicamente los comandos ejecutados. Para cada comprobación indica:

  • ¿Qué querías comprobar?
  • ¿Qué resultado has obtenido?
  • ¿Qué conclusión puedes extraer?
  • y, si existe un problema, ¿Cuál sería tu siguiente comprobación?
🩺 What should you remember?

Diagnosticar una red no consiste en probar comandos al azar. Empieza por tu propia máquina, comprueba interfaz → dirección → rutas → conectividad y utiliza cada resultado para decidir el siguiente paso.

Ya tenemos las herramientas necesarias para configurar y comprobar nuestra red.
